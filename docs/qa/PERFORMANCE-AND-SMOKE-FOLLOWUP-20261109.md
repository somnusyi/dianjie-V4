# 1.3.3 压力、接口与冒烟测试收尾

## 已上线版本的实测范围

- 原始证据：主工作区 `outputs/qa-20261109-online/RESULT.md` 及同目录 JSON。测试版隔离库承载业务模拟，正式版只做只读检查。
- 测试版五类角色（供应链、店长、厨师长、老板、供应商）分别完成两组 20 并发查询，每组每角色 30 次，共 300 次，全部返回 200。最慢一组 p95 为 467.3 ms。另有 5、10 并发阶梯；5 并发轮 200 次请求中 1 次 429，已定位旧版共享限流。
- 18 个核心角色接口均返回 200。扩展矩阵 40 次调用的 4 个 404 和 1 个 400 是测试路径或参数错误，改正后返回 200；老板反馈审批的 403 属另一项已决定移除的功能，不计作本次压力结果。
- 测试版完成采购、供应商发货、收货独立复审、门店订单与收货等业务流程；主要角色页面已打开。正式版没有创建或修改业务单据。
- 本次经 SSH 复核：正式和测试 API 的 `/health`、`/api/health` 均为 200；两站 `/v2/login` 均为 200。两个 API 和两个 Web 容器均为 healthy。

## 本地候选修复的边界压测

- 对尚未发布的账号限流修复，使用 Fastify 注入请求模拟同一反向代理后的两个账号，同时各发 200 次请求（总计 400 次）。400 次均返回 200；各账号第 201 次分别返回 429；额度用尽后 `/health` 仍返回 200。定向测试 7/7 通过。
- 这项证明本地候选在该并发和额度边界下按账号隔离；尚未在已上线镜像中复测，因此不能把线上旧共享限流问题写成已解决。

## 仍需说明的界限

- 正式版此前一次健康检查超时，随后恢复；现有证据未定位根因。当前主机可用内存约 539 MB，磁盘剩余约 3.4 GB。未在正式版增加并发压力。
- 20 并发是已完成的线上测试档位，并非系统容量上限。未覆盖超大数据量报表、断网、打印机、付款以及所有财务写入分支。
- 本轮没有部署、推送、修改正式业务数据或改变测试版业务数据。账号限流候选需在独立发布流程中先测试版、后正式版验证。

## 继续补测结果（本地候选源码，不代表线上镜像）

- API 非集成测试：1494 项中 1466 通过、21 失败、7 跳过；失败分布在 10 个文件。仓库入库和采购列表两组失败单独重跑仍复现，不能归因于测试文件之间互相干扰。失败包括旧模拟对象缺字段、旧状态预期与当前实现不一致；具体原因需逐项归类，不能以通过率代替验收。
- Web 测试：1383 项中 1305 通过、78 失败；其中商品页面 19 项受缺失 `getUser` 测试替身影响，采购页面 22 项受缺失 `pendingCounts` 模拟数据影响。其他失败涉及旧文案、旧按钮预期和部分交互断言，尚未逐项确认是测试过期还是页面故障。
- 本地隔离数据库的两批定向集成测试：第一批 48 通过、2 断言失败、10 项因建仓或流水前置条件未执行；第二批 41 通过、1 断言失败、44 项因旧建仓前置条件未执行。采购退货、批次质检、供应商库存预占、采购单可见性和月结的已执行测试通过。失败项中，供应商分类并发返回 `200/409` 而测试期待 `200/200`；采购收货异常路径返回 409 而测试期待 500，需核定当前业务契约。
- 最近两小时只读汇总两套 API 容器日志：正式版可解析请求状态中 519 次 200、1 次 400，没有 5xx；测试版 359 次 200，没有 5xx。这是窗口内日志观察，不证明其他时段无故障。
- 因以上失败和未执行项，**完整自动回归尚未通过**。本轮没有修改线上程序或业务数据；下一步应先修正过期测试前置条件和模拟数据，再重跑受影响测试，并对仍失败的业务断言做页面／接口复验。

## 已完成的进一步归类

- 采购页在订单列表响应缺少 `summary` 时会把待办计数设为 `undefined`，导致页面渲染失败。本地候选已加零值回退；不改真实订单或金额。商品、采购、库存报表和财务报表四组测试在补齐测试账号替身后 45/45 通过，Web 类型检查通过。
- 再跑完整 Web 回归为 1349 通过、34 失败，共 1383 项。剩余项分布于 18 个文件，主要包括旧按钮／文案断言、旧金额格式和部分实际交互断言，仍须逐项裁定。此前 78 项失败不能继续当作当前结果。
- 仓库入库和采购列表两个 API 单元测试文件单独重跑，仍有 8 项失败；不是测试文件之间的相互干扰。本地集成测试的建仓失败由当前数据库自动默认仓与旧测试手动建仓冲突触发，属于测试前置条件不符；这并不证明线上建仓失败。
- 已上线版本的五角色线上分级并发、接口与页面冒烟记录仍有效；上述本地回归失败不得混写为线上故障，也不得据此宣布系统全测通过。

- 同一隔离库的商品分类排序与供应商原子创建测试 **10/10** 通过。
- 库存报表与门店调拨集成测试补齐默认仓、余额及门店盘点基准后，最新为 **9/16 通过、7/16 失败**。调拨状态流转、导出及权限隔离已跑通；剩余失败中的库存金额来自没有净成本核定依据的旧测试造数，现行报表返回空金额／“待核算”。调拨汇总旧断言要求按输入的第二笔成本计算，而当前发货依门店冻结成本计算，仍需核对业务预期。导出把空成本显示为“待核算”，旧断言直接比较原始空值，也需要按展示契约重写。不能据这些旧断言认定线上报表故障，也不能把这组标为通过。
- 临时端口映射与 `dianjie_mouse_test` 已关闭并删除；`dianjie_feedback_test` 本地专用库在补测后再次创建，收尾时须删除。

## 额外复核

- 采购列表单元测试原来只模拟了订单数量查询，但现行接口还会同一事务汇总待办收货和差异；因此分页用例返回 500。补齐测试替身和待办汇总断言后，采购列表 **20/20** 通过，产品接口未改。
- 仓库手工入库旧单元测试仍期待“提交立即生成库存流水”，而当前代码是“提交待审核，复审后过账”；其模拟服务还缺少当前事务入口。这 7 项旧测试不能当作现行规则的通过证据，需按当前流程重写；上面的多人盘点实库测试已使用现行复审规则。

## 本地候选补测结论

- 商品目录曾把总仓商品一律标记为“下单强制库存校验”，与订单提交接口按 `blockZeroStockAtOrderEntry` 决定是否强制的规则不一致。已在本地对齐标记，商品目录 8/8、网页下单库存策略 7/7 通过；不改库存、订单或线上镜像。
- 按确认过的规则更新旧测试：供应商无报价留空、账务中文状态和两位金额、北京时间文件名、盘点搜索只全选可见商品、盘点复盘审核及质检按商品批次查看。对应定向回归通过。
- 最新全量非集成回归（本地候选）：API **1479 通过、8 失败、7 跳过**（1494 项，五角色混合限流测试加入前）；Web **1366 通过、17 失败**（1383 项）。API 剩 7 项旧手工入库 mock/立即过账断言及 1 项已暂停的 AI 自动修复源码断言；Web 剩余主要是旧库存页操作、旧审核文案/版式及旧合同测试。它们不能写成通过，也没有证据表明对应线上页面均故障。完整自动回归仍需单独收尾。
