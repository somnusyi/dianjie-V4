# 配送成本利润与门店补货实施记录（2026-09-28）

## 范围与非范围

- 来源：`2026-09-24-四场会议改动问题与审核方案.md` 中的“门店补货单”与“配送单·成本利润与导出”。
- 本记录不实现自动采购建议，不把补货当原订货单改金额，不直接修改已收货单据。
- 本记录不把 `DeliveryOrder` 改造为订货单/补货单双来源；现有配送、预占、出库、收货、报损和结算始终通过正式 `PurchaseOrder` 履约。
- 不提交、不推送、不部署。

## 配送成本利润（已实现小切片）

### 唯一数据口径

- 发货单价及原发货金额：`DeliveryOrderItem.unitPriceSnapshot/amount`，不读当前商品价格。
- 成本：`WarehouseLedgerMovement` 中 `ORDER_OUTBOUND + DeliveryOrder`的冻结出库成本。
- 成本流水必须同时匹配配送单、原订货行和商品；任一项不一致即保持空成本并显示勾稽告警，禁止把其他物品成本挂入本行。
- 返货、报损冲回、配送撤销：只认 `ReceiptRejectionReversal`、`LossClaimReversal`、`DeliveryOrderShipCancel` 三类 `REVERSAL`。
- 净结算金额：原冻结发货金额扣除上述业务冲回。
- 利润：净结算金额减冻结出库成本。任一行缺成本或无法勾稽时，单据成本和利润为 `null`，页面显示“—”，不按0计算。
- 发货数量与台账勾稽：原出库数量 = 当前发货数量 + `DeliveryOrderShipCancel`冲回数量。收货拒收/报损冲回不改写原发货数量，但会冲减净结算量及净结算金额。

### 页面与权限

- 入口：供应链“配送单查询”列表的“查看明细”。
- 列表：原发货金额、成本金额、利润；缺成本时提示进入明细看告警。
- 明细：商品/规格/单位、接单数量、发货数量、发货单价、原发货金额、净结算金额、成本单价、成本金额和利润。
- 桌面使用明细表，手机使用分行卡片；列表、详情、列表 Excel 和单张明细 Excel 复用同一投影服务。
- 仅 `SUPPLY_CHAIN` 接收成本利润投影并可导出明细；门店及供应商角色的响应不包含内部成本字段。

## 门店补货单（功能已实现并通过 ZCode 分段审查）

### 模型

- `ReplenishmentOrder`：租户、补货单号、门店、供应商、期望到货日、状态、备注、创建来源、创建人/提交人/接单人/取消人及时间、`rowVersion`、`idempotencyKey`。
- `ReplenishmentOrderItem`：补货单、商品、补货数量、冻结订货单位/单价/金额与商品快照。单价只沿用现有订货定价及审批边界，补货入口不另开改价绕过。
- `ReplenishmentOrderEvent`：补货单状态转换、操作人、角色、请求号、IP 及元数据，不覆盖历史。
- `ReplenishmentFulfillmentLink`：补货单与接单时生成的正式 `PurchaseOrder` 一对一唯一链接。不修改 `DeliveryOrder.purchaseOrderId` 及 `DeliveryOrderItem.purchaseOrderItemId` 的必填不变式。
- 所有门店、供应商、操作人、事件操作人和正式订单链接均以 `tenantId + id` 复合外键约束，数据库层拒绝跨租户错连。

### 状态机

|from → to|触发者|预定 API|关键事实|
|---|---|---|---|
|新建 → `DRAFT`|SUPPLY_CHAIN|`POST /api/replenishment-orders`|按租户+创建人+幂等键防重，保存创建来源/操作人|
|`DRAFT` → `SUBMITTED`|SUPPLY_CHAIN|`POST /:id/submit`|冻结商品、单位、单价和金额|
|`SUBMITTED` → `ACCEPTED`|SUPPLY_CHAIN 内部接单|`POST /:id/accept`|Serializable + `rowVersion`，同一事务创建正式 `PurchaseOrder`、明细、事件及唯一 Link|
|`DRAFT`/`SUBMITTED` → `CANCELLED`|SUPPLY_CHAIN|`POST /:id/cancel`|未生成正式履约时才允许，原因和操作人必填|

数据库只接受上述人工命令状态；`FULFILLING`、`COMPLETED` 和 `EXCEPTION` 均为只读投影，任何 API 不得直接写入：

- 正式订单进入配送/待确认/收货但尚未完结时，投影为 `FULFILLING`；只有正式订单整体 `COMPLETED` 才投影为 `COMPLETED`，不以第一张配送单已收货提前结束。
- `ACCEPTED` 缺 Link/正式订单、正式订单被取消，或 `DRAFT`/`SUBMITTED`/`CANCELLED` 已存在 Link，均投影为 `EXCEPTION` 并突出“处理异常”，不得静默显示成正常状态。
- `DELIVERY_CREATED` 只记事件，不作业务状态；一张正式订货单可以多次配送。

### 页面流程

- 一级：配送管理；二级：门店补货单，与“门店订货单”、“配送单”分开。
- 列表顺序：补货单号、门店、供应商、期望到货日、商品摘要、状态、创建来源、创建时间、创建人、备注、操作。
- 新建顺序：门店 → 供应商 → 期望到货日 → 商品/规格/单位/补货数量/冻结单价/金额 → 备注 → 保存草稿或提交。
- 每个状态只突出一个下一步：草稿继续编辑，已提交接单，已接单查正式订单，履约中查配送，已完成查收货，异常状态处理异常。
- 空态直达“新建补货单”；提交失败保留草稿输入；手机端商品行优先保留数量和单位；打印/导出与列表的补货来源及字段一致。
- 门店只能查看自己门店的补货与后续配送/收货；供应商仅限自己；供应链代建及接单的操作人、来源和事件必须可追溯。
- API 的列表/详情共用最小响应 DTO，只返回门店/供应商编号与名称、冻结商品字段、业务状态和正式订单最小链接；不返回供应商银行、税务、请求指纹、IP 等内部字段。
- 草稿支持 `PATCH` 继续编辑：`rowVersion` CAS、重新校验门店/供应商/商品、重新冻结价格单位、原子替换明细并记录 `EDITED` 事件；提交后禁止再编辑。
- 列表筛选接受 `FULFILLING`、`COMPLETED`、`EXCEPTION` 等页面业务状态，并把正式订单状态条件下推到数据库，使筛选、总数和分页使用同一条件。
- 供应链入口已按“配送管理 → 门店补货单”落地；与门店订货单、配送单并列，页面反复提示“独立补货，不调整原订货单”。
- 供应链列表同时提供桌面表格与移动卡片；店长工作台增加“本店补货进度”只读入口，门店只看本店且草稿不可见。
- 草稿、待接单、已接单、履约中、已完成、异常分别只有一个突出下一步；配送、收货深链会把正式订单号带入目标页筛选。
- 草稿支持离开保护、409 冲突刷新、取消原因危险确认；失效商品保留冻结快照并标红，移除前禁止提交。
- 提交发现目录价变化时返回结构化价格差异；页面逐项展示旧价→新价和涨/降金额。“暂不更新”不写入，只有确认后才重算并保存新冻结价。
